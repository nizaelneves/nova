# Mem0 funciona no Phibe, mas custa mais que vale

O Mem0 é uma camada de memória de longo prazo, com licença Apache 2.0, que usa um LLM para extrair fatos duráveis das conversas e depois recuperá-los por busca ([GitHub](https://github.com/mem0ai/mem0)). O SDK Python é o pacote `mem0ai` (import `mem0`), versão **2.2.1 de 25/09/2026**, com Python >=3.10,<4.0 ([PyPI](https://pypi.org/project/mem0ai/)). A autenticação na nuvem usa uma chave de API (variável `MEM0_API_KEY`), mas para um assistente local-first a rota coerente é a versão open source (OSS) com Ollama, que mantém os dados na máquina. Tecnicamente isso é viável, porém frágil: a extração de fatos depende de JSON válido do LLM, e há relatos de falhas com modelos pequenos. Com contexto de ~4096 tokens, qwen3.5:4b e um `knowledge.db` que já faz busca híbrida, o ganho líquido é pequeno. Minha recomendação é não adotar o Mem0 agora. Vale começar com uma tabela `memories` no próprio `knowledge.db`, e só reavaliar o Mem0 depois de um teste local de extração. Ressalva: as notas vieram de resumos de páginas de documentação, e nada foi testado no código do Phibe.

## Como o Mem0 extrai, guarda e recupera memórias

O Mem0 existe em duas formas: a Platform hospedada (com chave de API) e o OSS autohospedado (biblioteca ou stack Docker) ([Intro](https://docs.mem0.ai/introduction)). O laço típico é `search` por `user_id`, injeção do resultado no prompt de sistema, geração da resposta e depois `memory.add(conversa)` ([GitHub](https://github.com/mem0ai/mem0)). O `add` segue quatro etapas: busca memórias relacionadas já existentes para não repetir; um LLM extrai preferências, decisões e planos (fatos, não a transcrição); deduplica e gera embeddings; e extrai entidades, que viram nós de Graph Memory na Platform ([How it works](https://docs.mem0.ai/core-concepts/how-it-works)). Cada `add` custa, portanto, **pelo menos uma chamada de LLM mais embeddings**. Isso é inferência das notas, e o número exato de chamadas por `add` no OSS não está documentado nas páginas lidas.

A gravação é aditiva. Se o usuário diz "mudei de Austin para Seattle", entra um fato novo e o antigo não é reescrito. Correções exigem `update` ou `delete` explícitos ([How it works](https://docs.mem0.ai/core-concepts/how-it-works)). A busca combina quatro sinais: semântico, palavra-chave, reforço por entidade e temporal. Na Platform a fusão é gerenciada; no OSS o ranking depende do vetor store e de um reranker opcional, e o sinal de entidade não tem grafo ([How it works](https://docs.mem0.ai/core-concepts/how-it-works)). O armazenamento é dividido em SQL (fatos e metadados), banco vetorial e entity store.

O escopo é feito por `user_id`, `agent_id`, `run_id` e, só na Platform, `app_id`. As leituras usam um dicionário `filters`, e os campos não citados ficam livres. Há uma armadilha: por padrão `user_id` e `agent_id` vão para registros separados, então um `AND` entre os dois retorna vazio ([Entity-scoped memory](https://docs.mem0.ai/platform/features/entity-scoped-memory)). Para um assistente de usuário único, basta um `user_id` estável, um `run_id` opcional por conversa e metadados para categorias (inferência das notas). Os números de benchmark do README (LoCoMo 92,5; LongMemEval 94,4) são autorrelatados e, segundo o próprio README, refletem a Platform gerenciada; o OSS teria ganhos "direcionalmente semelhantes" ([GitHub](https://github.com/mem0ai/mem0)). Não devem ser tratados como expectativa para um modelo de 4B.

## Instalação e uso do SDK Python: nuvem com chave, OSS sem chave

O pacote core é leve. Depende de qdrant-client, pydantic, openai, httpx, posthog, sqlalchemy e protobuf (>=5.29.6,<7) ([pyproject.toml](https://raw.githubusercontent.com/mem0ai/mem0/main/pyproject.toml)). Os extras `llms`, `vector-stores` e `extras` puxam dezenas de dependências (litellm, torch via sentence-transformers e outras) e devem ser evitados. O cliente `ollama` fica no extra `llms`, não no core, então a instalação mínima para o Phibe seria `pip install mem0ai ollama` ([pyproject.toml](https://raw.githubusercontent.com/mem0ai/mem0/main/pyproject.toml)). Como o pyproject citado é o da branch main, e não o da 2.2.1 publicada, vale rodar `pip install --dry-run` para detectar conflito de pins (pydantic, protobuf) com o resto do projeto.

Na nuvem, a chave é gerada em app.mem0.ai, nas configurações de API keys. O cliente lê `api_key or os.getenv("MEM0_API_KEY")` ([client/main.py](https://raw.githubusercontent.com/mem0ai/mem0/main/mem0/client/main.py)). O exemplo oficial do quickstart é este ([Platform quickstart](https://docs.mem0.ai/platform/quickstart)):

```python
from mem0 import MemoryClient
client = MemoryClient(api_key="your-api-key")
client.add(messages, user_id="user123")
results = client.search("What are my dietary restrictions?", filters={"user_id": "user123"})
```

Para FastAPI existe `AsyncMemoryClient`, que evita bloquear o event loop ([Async client](https://docs.mem0.ai/platform/features/async-client)). Na Platform o `add` é assíncrono: devolve `status: PENDING` e um `event_id` consultável ([Add](https://docs.mem0.ai/core-concepts/memory-operations/add)). Há duas inconsistências documentais. O guia de migração diz que `update()` não existe na Platform, mas o código-fonte do cliente o define ([migration](https://docs.mem0.ai/migration/oss-to-platform)). E o construtor atual não aceita `org_id`/`project_id`, embora fontes antigas ainda os mostrem. Nenhum dos dois pontos importa para a rota OSS.

No OSS, `Memory()` usa por padrão OpenAI (`gpt-5-mini`, `text-embedding-3-small`), Qdrant em `/tmp/qdrant` e histórico SQLite em `~/.mem0/history.db` ([OSS overview](https://docs.mem0.ai/open-source/overview)). Para ficar 100% local, usa-se `Memory.from_config` com `ollama` no LLM e no embedder. O exemplo oficial completo usa Qdrant em `localhost:6333`, `llama3.1:latest`, `nomic-embed-text:latest` e `embedding_model_dims: 768`, que **precisa casar com o modelo de embedding** ([Mem0 with Ollama](https://docs.mem0.ai/examples/mem0-with-ollama)). Os defaults de dimensão (512 no embedder, 1536 no Qdrant) causam descompasso se não forem ajustados. Há relatos de erro de dimensão em issues do projeto ([GitHub #3391](https://github.com/mem0ai/mem0/issues/3391)). Uma configuração adaptada ao Phibe seria:

```python
config = {
  "llm": {"provider": "ollama", "config": {"model": "qwen3.5:4b", "temperature": 0.1,
          "max_tokens": 2000, "ollama_base_url": "http://localhost:11434"}},
  "embedder": {"provider": "ollama", "config": {"model": "nomic-embed-text",
          "embedding_dims": 768, "ollama_base_url": "http://localhost:11434"}},
  "vector_store": {"provider": "qdrant", "config": {"collection_name": "phibe",
          "embedding_model_dims": 768, "path": "C:/Projects/Jarvis/data/qdrant", "on_disk": True}},
}
```

Essa configuração é montada a partir das páginas por componente e **não foi testada**. O nome da chave `ollama_base_url` no bloco `llm` e a existência do modo Qdrant embarcado com Ollama não foram confirmados, já que o exemplo oficial usa um servidor na porta 6333. O modo `path` provavelmente trava a pasta para um único processo (conhecimento geral, não das notas), o que impede múltiplos workers do uvicorn. O modelo também precisa suportar tool calling ([Ollama LLM](https://docs.mem0.ai/components/llms/models/ollama)), o que o qwen3.5 provavelmente atende, mas não foi verificado.

## Privacidade, telemetria e o que a nuvem exigiria

Na Platform, o texto passado ao `add` vai para os servidores do Mem0 para extração e armazenamento. Num assistente pessoal isso é dado privado do usuário, o que contradiz a premissa local-first. O MCP hospedado (`https://mcp.mem0.ai/mcp`, 11 ferramentas) e o plugin do Claude Code seguem o mesmo modelo, com memórias guardadas na conta Mem0 ([Mem0 MCP](https://docs.mem0.ai/integrations/mcp), [Claude Code](https://docs.mem0.ai/integrations/claude-code.md)). Não encontrei MCP oficial totalmente local; existe indício de um caminho OpenMemory com Ollama no repositório, de manutenção não verificada ([issues](https://github.com/mem0ai/mem0/issues?q=ollama+windows)). A lista de integrações (cerca de 22 entradas) é dominada por frameworks como LangChain, CrewAI e LangGraph, além de voz (Livekit, Pipecat), observabilidade e low-code ([Integrations](https://docs.mem0.ai/integrations)). Nenhuma delas é relevante para um FastAPI próprio. A superfície útil é a classe `Memory` e, opcionalmente, o MCP.

Mesmo o OSS com Ollama não é silencioso. A telemetria vem ligada e envia a `https://us.i.posthog.com` versão, sistema operacional, um `distinct_id` (o id de usuário ou e-mail, se informado) e, no OSS, nome da coleção e classes de LLM, embedder e vector store. Desliga-se com `MEM0_TELEMETRY=false` ([telemetry.py](https://raw.githubusercontent.com/mem0ai/mem0/main/mem0/memory/telemetry.py)). Como o `distinct_id` pode ser o `user_id`, convém usar um identificador opaco no Phibe. Segundo o código lido, a variável deve estar definida antes do import de `mem0`. Ainda não está verificado se o OSS configurado com Ollama envia algo além da telemetria. Depois de integrar, vale conferir por captura de rede. A conta gratuita da Platform não exige cartão e dá 10.000 adds e 1.000 buscas por mês nos primeiros 30 dias, depois 50.000 adds e 10.000 buscas com chave de LLM própria. O grafo fica restrito ao plano Custom ([Pricing](https://mem0.ai/pricing)). Esses preços foram lidos por resumo e devem ser conferidos ao vivo.

## Encaixe no Phibe: contexto de 4096 tokens e sobreposição com o knowledge.db

O padrão viável é buscar antes de responder, injetar poucas memórias curtas e gravar depois do turno, fora do caminho crítico. A busca custa um embedding mais uma consulta vetorial, sem LLM. Já o `add` com inferência exige que o LLM devolva JSON válido, e é aí que modelos pequenos falham. Há relatos de `Error in new_retrieved_facts: Expecting value...` ao usar Ollama com llama3.1/3.2, qwen3:8b e deepseek-r1. O mantenedor atribui o problema a alucinação do LLM sob recursos limitados, e os contornos são `infer=False`, instalar da branch git ou usar um modelo menor ([GitHub #3391](https://github.com/mem0ai/mem0/issues/3391)). Reclamações de 2026 indicam que o problema não está plenamente resolvido. Há também um relato de timeout no Windows 11 sem Docker ([issues](https://github.com/mem0ai/mem0/issues?q=ollama+windows)).

As estimativas a seguir são minhas, sem fonte, e devem ser medidas. Com SOUL.md, USER.md, schemas de ferramentas e histórico já ocupando boa parte dos 4096 tokens, a injeção deveria ficar em 3 a 5 memórias de ~15 a 25 tokens (cerca de 100 a 150 tokens), com limiar de similaridade para injetar zero quando nada for relevante. O `add` deveria rodar em `BackgroundTasks` ou fila, em lote ou em ociosidade, para não competir pela GPU com a próxima resposta. O modo de pensamento do qwen3.5 pode emitir tokens de raciocínio que quebram o JSON, e desligá-lo nas chamadas do Mem0 é prudente, mas não foi verificado para esse modelo. Manter o embedder residente (`keep_alive`) evita pagar o carregamento a cada consulta, ao custo de disputar VRAM com o modelo de chat.

A sobreposição é o argumento mais forte contra a adoção. O `knowledge.db` já faz recuperação (bm25 mais vetor), o USER.md guarda fatos estáveis do usuário, e o Mem0 extrairia justamente "preferências e fatos", colidindo com o USER.md. Como a gravação é aditiva, fatos contraditórios convivem. Entrariam ainda um segundo banco vetorial (Qdrant), um segundo caminho de embeddings, dependências extras e telemetria. Duas ressalvas: essas conclusões se apoiam na descrição do Phibe dada no pedido, não numa leitura do código, e as notas de memória do projeto lembram que o chat ainda não lê o `knowledge.db`, então a decisão sobre memória deve andar junto com essa ligação. A alternativa mais barata é uma tabela `memories` no `knowledge.db`, reaproveitando a busca híbrida e um prompt de extração pequeno. Se mesmo assim o Mem0 for adotado, o receituário é: Ollama para LLM e embedder, caminho explícito do Qdrant na pasta de dados do usuário (o padrão `/tmp/qdrant` não é durável), `MEM0_TELEMETRY=false`, sem chave da Platform e sem MCP hospedado. O USER.md permanece como fonte autoritativa, e o montador de prompt deduplica contra ele.

## Conclusão

A principal conclusão é que o Mem0 vende extração e atualização de memória, e justamente essa parte é a mais frágil num modelo de 4B local, enquanto a parte que o Phibe já domina (armazenar e buscar) é a que o Mem0 duplicaria. Em termos de decisão, o risco real não é instalar o pacote, que é simples, mas a qualidade da extração, a duplicação com USER.md e o egress acidental de dados pela telemetria ou pela Platform.

O próximo passo de menor custo é um experimento de uma tarde: rodar o `Memory.from_config` com Ollama sobre 20 a 30 turnos reais do Phibe e medir a taxa de falha do JSON de extração, a latência de `search` e `add` e o consumo de VRAM. Se a taxa de falha for alta, o caminho é a tabela `memories` própria, possivelmente com `infer=False` e fatos já estruturados pelo summarizer do Phibe. Pontos em aberto nas notas: versão de extração do OSS, comportamento de atualização e deduplicação, parâmetros de top_k e limiar, e se o Qdrant embarcado funciona com essa pilha no Windows.
