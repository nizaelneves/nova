# Cognee docs audit: Core API, Pipelines and Operations (v1.6.x, as of 2026-11-14)

Scope note: read from docs.cognee.ai (markdown shards via llms-core.md / llms-api.md) plus raw `cognee/api/client.py` and `generate_graph_prompt.txt` from GitHub. Latest release per changelog is 1.6.8 (Nov 12, 2026). I did NOT read the GitHub source for update/delete/pipeline internals; everything below marked "docs" is from documentation pages. Several docs pages fetched via a summarizing model, so exact wording may be slightly paraphrased.

## 1. Python API surface: add, cognify, search, remember/recall/improve/forget, memify, update (v1.6)

### Takeaway
There are two API generations. "V2" is remember/recall/improve/forget (remember = add + cognify + improve). The old add/cognify/search/memify/delete are labelled "legacy" in docs; memify and delete are deprecated, update is NOT deprecated. For a notes second brain, add + cognify (or remember) + search/recall + datasets.delete_data + update is the supported path.

### Cited Findings
- Docs split operations into main ops (Remember, Recall, Improve, Forget, Serve, Push) and "legacy-operations" (Add, Cognify, Search, Memify, Delete) — [llms-core index](https://docs.cognee.ai/llms-core.md)
- `remember(data, dataset_name="main_dataset", *, session_id, chunk_size, chunker, custom_prompt, run_in_background=False, self_improvement=True, session_ids, dry_run, raise_on_error=True, **kwargs)`. Without `session_id` it runs add then cognify; with `session_id` writes only to session cache. By default runs `improve()` afterward. kwargs include `graph_model`, `extractor`, `summary_method`, `node_set`, `dataset_id`, `incremental_loading`, `data_per_batch`, `chunks_per_batch`, `config`, `user`, per-call `llm_config`/`embedding_config`. `temporal_cognify` is deprecated/ignored — [remember()](https://docs.cognee.ai/python-api/remember.md)
- `remember()` returns `RememberResult` (status, dataset_id, pipeline_run_id, improve, improve_error, after_run_error...). `dry_run=True` returns a token/USD estimate without LLM calls (excludes improve and embeddings) — [remember()](https://docs.cognee.ai/python-api/remember.md)
- `add(data, dataset_name='main_dataset', user, node_set, ..., dataset_id, preferred_loaders, incremental_loading=True, data_per_batch=20, importance_weight=0.5, run_in_background=False, data_cache=True, ...)`. Does not build graph and does not need an LLM key. Accepts text, paths (abs, file://, s3://), URLs, DataItem, uploads, lists. Returns PipelineRunInfo including `data_ids` (use these for later update/delete) — [add()](https://docs.cognee.ai/python-api/add.md)
- `cognify(datasets=None, user, graph_model=KnowledgeGraph, chunker=TextChunker, chunk_size=None, chunks_per_batch, config, run_in_background=False, incremental_loading=True, custom_prompt, data_per_batch=20, data_cache=True, dry_run, raise_on_error=True, chunk_attachment, extractor, ontology_file_path, summary_method, early_chunk_indexing)`. `datasets=None` processes ALL of the user's datasets. Runs `indexing_pipeline` (no LLM; chunk search becomes available) then `cognify_pipeline` — [cognify()](https://docs.cognee.ai/python-api/cognify.md)
- Cognify defaults: `SUMMARY_METHOD=from_extraction` (no LLM per chunk; "llm" = one call per chunk), `GRAPH_EXTRACTOR=auto` (falls back to local GLiNER if no LLM key), `EARLY_CHUNK_INDEXING` on. Config is cached per process, so set env before first call — [cognify()](https://docs.cognee.ai/python-api/cognify.md)
- Cognify statuses: PipelineRunStarted/Yield/Completed/AlreadyCompleted/Errored; PipelineRunProgress only on WebSocket — [cognify()](https://docs.cognee.ai/python-api/cognify.md)
- `search(query_text, query_type=HYBRID_COMPLETION, user, datasets, dataset_ids, system_prompt_path, system_prompt, top_k=15, node_type=NodeSet, node_name, node_name_filter_operator="OR", only_context, session_id, wide_search_top_k, triplet_distance_penalty, feedback_influence, verbose, retriever_specific_config, neighborhood_depth, include_references, llm_config, ...)`. Default search type is HYBRID_COMPLETION, not GRAPH_COMPLETION. Name lookup in `datasets` only covers owned datasets; shared need `dataset_ids`. Empty graph raises NoDataError (404); populated graph with no match returns [] — [search()](https://docs.cognee.ai/python-api/search.md)
- `recall(query_text, query_type=None, *, datasets, dataset_ids, top_k=15, auto_route=True, scope, **opts)` returns Pydantic objects (use `result.text`), reads only existing memory, rule-based (no LLM) routing: quoted query -> CHUNKS_LEXICAL; coding-rules phrase -> CODING_RULES; code identifier -> CODE; "how many" -> BROAD; time preposition + absolute date -> TEMPORAL; else HYBRID_COMPLETION. Without usable LLM key it returns the assembled prompt (only_context). `score` is distance, lower is better, only for CHUNKS/SUMMARIES/SKILLS. Chunk metadata has `data_id`, `chunk_id`, `chunk_index`, `document_name` — [recall()](https://docs.cognee.ai/python-api/recall.md)
- Recall warm-up: cold dataset returns a `system` item `memory_warming_up`; failed build returns `build_failed` with error class/message — [recall()](https://docs.cognee.ai/python-api/recall.md)
- `improve(dataset="main_dataset", *, run_in_background, node_name (deprecated), session_ids, build_global_context_index, build_truth_subspace, review_conflicts)` runs nine named stages; global context index built by default w/o LLM; conflict review on by default since 1.6.6 (it was off in <=1.6.5), uses LLM on up to 25 entities / 8000 tokens per call; marks facts current/superseded/conflicting; returns `ImproveResult` with stages — [improve()](https://docs.cognee.ai/python-api/improve.md)
- With defaults (`IMPROVE_DEBOUNCE_ENTRIES=1`), every `remember(session_id=...)` triggers an improve; `IMPROVE_AUTO_ENABLED=false` disables auto-improve — [improve()](https://docs.cognee.ai/python-api/improve.md)
- `memify()` is deprecated (FutureWarning on every call), replaced by `improve()` and `run_custom_pipeline()`; with no tasks it does nothing and returns `{}`; no default tasks remain (triplet embeddings removed) — [memify()](https://docs.cognee.ai/python-api/memify.md); deprecated in 1.6.5 incl. `POST /api/v1/memify` and CLI — [changelog](https://docs.cognee.ai/changelog.md)
- `cognee.delete(data_id, dataset_id, mode="soft")` deprecated since 0.3.9; use `cognee.datasets.delete_data(dataset_id=, data_id=)` — [delete()](https://docs.cognee.ai/python-api/delete.md). `DELETE /api/v1/delete` deprecated in 1.6.6 — [changelog](https://docs.cognee.ai/changelog.md)
- `forget(*, data_id, dataset, dataset_id, everything=False, memory_only=False, clean_history=False, user)`: data_id needs dataset; item delete returns receipt (`deleted_nodes`, `deleted_edges`, `data_record_found`, `data_remaining`, `dataset_deleted`); `status="not_found"` without error if no match; `memory_only` clears graph+vector but keeps raw files and Data rows (re-cognifiable); no mode scrubs bytes from disk; no soft delete — [forget()](https://docs.cognee.ai/python-api/forget.md); [memory versioning](https://docs.cognee.ai/core-concepts/further-concepts/memory-versioning.md)

#### SearchType values and when to use (docs table)
- No LLM: `CHUNKS` (raw passages by vector similarity), `SUMMARIES` (pre-generated summaries), `CHUNKS_LEXICAL` (BM25-style keywords, exact matches), `CYPHER` (raw rows; off unless `ALLOW_CYPHER_QUERY=true`, needs Ladybug/Neo4j), `CODE`, `SKILLS`, `CODING_RULES`.
- 1 LLM call: `RAG_COMPLETION` (chunks then answer), `HYBRID_COMPLETION` (chunks+summaries+graph; default and "best general balance"), `GRAPH_COMPLETION` (graph context; "most queries").
- More calls: `HYBRID_COMPLETION_DECOMPOSITION` (2), `GRAPH_SUMMARY_COMPLETION` (3), `TEMPORAL` (~3; extracts time window and reranks by date), `GRAPH_COMPLETION_CONTEXT_EXTENSION` (~6), `GRAPH_COMPLETION_DECOMPOSITION` (5-8), `GRAPH_COMPLETION_COT` (~14), `NATURAL_LANGUAGE` (NL->Cypher, up to 3 attempts, off by default), `GRAPH_REPORT` (1), `BROAD` (1-3; whole-dataset counts/totals), `FEELING_LUCKY` (2-5; LLM picks type), `AGENTIC_COMPLETION` (needs exactly one dataset; up to 6 tool rounds). `TRIPLET_COMPLETION` deprecated -> runs as GRAPH_COMPLETION. Call counts are benchmark figures, not guarantees — [SearchType](https://docs.cognee.ai/python-api/search-type.md)
- `RAG_COMPLETION`/GRAPH/HYBRID with `only_context=True` return the prompt with no LLM call (useful for "retrieve and let Phibe's own LLM answer") — [search()](https://docs.cognee.ai/python-api/search.md)
- `neighborhood_depth` or `feedback_influence > 0` silently switch HYBRID_COMPLETION to GRAPH_COMPLETION — [search()](https://docs.cognee.ai/python-api/search.md)

### Inferences
- For a notes app that wants its own LLM to answer: `CHUNKS` (+ `document_name`/`data_id` in metadata for citations) or `only_context=True` completions avoid double LLM spend; TEMPORAL only helps if dates are extracted (default pipeline extracts dates as Timestamp nodes).
- Avoid `remember()` default self_improvement for bulk note loads (improve + conflict review adds LLM calls per remember); consider `self_improvement=False`, run `improve()` once later.
- Using `cognify(datasets=None)` is a footgun: it processes every dataset.

### Gaps
- Exact default prompt for `temporal` and per-type system prompts not read.
- Did not read legacy `search`/`cognify` concept pages or `run_custom_pipeline`.
- `SearchResult` precise JSON shape per type not confirmed (docs only say shape varies).

## 2. Datasets, data_id, node_set, custom graph models/ontology, custom prompts, chunking, incremental loading

### Takeaway
Datasets are the isolation boundary; node_set is only a tag/filter inside a dataset. The extraction prompt CAN be fully replaced via `custom_prompt`, but there is NO documented feature for "English canonical name + original-language alias"; that would need a custom prompt and/or custom `graph_model` (verify empirically).

### Cited Findings
- Dataset is the isolation boundary in multi-user mode (own graph + vector store per dataset); tenants are groups sharing permissions, not DBs; in single-user mode (`ENABLE_BACKEND_ACCESS_CONTROL=false`) one shared graph/vector serves all datasets and `datasets` filters are ignored — [Data isolation](https://docs.cognee.ai/core-concepts/multi-user-mode/data-isolation-and-multi-tenancy.md)
- `node_set` must be a list of non-empty strings; invalid raises `InvalidNodeSetError`. Tags flow to Documents, Chunks, entities as `NodeSet` nodes with `belongs_to_set` edges. It is "a retrieval filter, not an isolation boundary": scoped search includes the set node, directly linked nodes and edges between them, so cross-set relations can leak into answers. Entities are deduplicated by name across sets — [NodeSets](https://docs.cognee.ai/core-concepts/further-concepts/node-sets.md)
- `DataItem` lets you attach `label`, `external_metadata`, `node_set` or a stable `data_id`; label/metadata stored on Data record, copied onto chunks but not embedded (surfaced via HYBRID_COMPLETION) — [add()](https://docs.cognee.ai/python-api/add.md)
- `custom_prompt` fully replaces the default extraction prompt (cognify/remember/update). `system_prompt` is for query-time answers; mixing them "will silently have no effect". Default graph prompts chosen via `GRAPH_PROMPT_PATH`. REST `POST /api/v1/cognify` has `customPrompt`; there is also `/api/v1/llm` generate-custom-prompt and infer-schema — [Custom prompts](https://docs.cognee.ai/guides/custom-prompts.md); [cognify REST](https://docs.cognee.ai/api-reference/cognify/cognify-low-level:-build-the-knowledge-graph-from-already-added-data.md)
- Default extraction prompt (GitHub): nodes need a `name` using the most complete human-readable name; coreference rule says use the entity's most complete identifier everywhere; basic type labels ("Person" not "Engineer"); Timestamp nodes normalized YYYY/YYYY-MM-DD; snake_case relation names. Nothing about language of names — [generate_graph_prompt.txt](https://raw.githubusercontent.com/topoteretes/cognee/main/cognee/infrastructure/llm/prompts/generate_graph_prompt.txt) (summarized by fetch tool, not verbatim)
- Multilingual: per-chunk `langdetect` (55 languages, chunks <10 chars skipped); optional `translate_content` task between chunking and graph build replaces `chunk.text` with translation (target `TARGET_LANGUAGE` default `en`, `CONFIDENCE_THRESHOLD` 0.8, provider `llm`/google/azure) and keeps original in a `TranslatedContent` data point. It is a custom-pipeline task, not in default cognify. Page says nothing about entity-name language or aliases — [Multilingual ingestion](https://docs.cognee.ai/guides/multilingual-ingestion.md)
- `graph_model` accepts a custom `DataPoint` subclass (default `KnowledgeGraph`); `chunk_attachment` needs a custom DataPoint model. Guides exist: Custom Graph Model, Graph Model from JSON — [cognify()](https://docs.cognee.ai/python-api/cognify.md); [guide index](https://docs.cognee.ai/llms-core.md)
- Ontology: `ontology_file_path` (comma-separated), modes `annotate` (default) or `strict` (drops ungrounded entities); REST uses uploaded `ontologyKey`; as of 1.6.8 searches use `ONTOLOGY_FILE_PATH` by default and a malformed ontology file makes them raise — [cognify()](https://docs.cognee.ai/python-api/cognify.md); [changelog](https://docs.cognee.ai/changelog.md)
- Chunkers: `TextChunker` (default; paragraph-based, no overlap), `CsvChunker`, `LangchainChunker` (needs `cognee[langchain]`; overlap 10 words), `TextChunkerWithOverlap` (`chunk_overlap_ratio`). `chunk_size` is max tokens; default = min(embedding limit, half LLM max completion tokens). Text without boundaries is emitted as one oversized chunk. REST `/cognify` does NOT take `chunk_size`; set env (doc says default 1500) — [Chunkers](https://docs.cognee.ai/core-concepts/further-concepts/chunkers.md)  (note: cognify() page gives a different default formula; the chunkers page's "1500" env default is listed only for REST)
- Incremental loading: `incremental_loading` and `data_cache` both default True; skipping happens if either is true; force re-ingestion needs both False. Documents already completed for the same pipeline are `PipelineRunAlreadyCompleted` — [add()](https://docs.cognee.ai/python-api/add.md); [Pipelines](https://docs.cognee.ai/core-concepts/building-blocks/pipelines.md)

### Inferences
- English canonical + original alias: options are (a) `custom_prompt` instructing English canonical `name` plus alias list — but a custom prompt REPLACES the default, so it must re-state the useful default rules (timestamps, naming, snake_case relations, coreference); (b) custom `graph_model` DataPoint with `aliases: list[str]` and `original_name`; (c) translate-first pipeline (loses original text in graph; keeps it in TranslatedContent). None confirmed by docs; needs a test. Combining a custom prompt or custom graph_model forces a full rebuild on `update()` (see Q3), so adopt one before bulk ingesting.
- Entities dedupe "by name"; if names vary by language the same concept splits into separate nodes, which supports forcing English canonical names.
- node_set per note type/tag is fine for filtering, but not for privacy; separate datasets for hard separation.

### Gaps
- No doc confirmation that custom_prompt can enforce alias fields without a matching graph_model.
- Did not read custom-graph-model / graph-model-from-json / ontology pages in detail.
- Default chunk_size value inconsistent across pages (formula vs "1500" env default); not resolved.

## 3. Editing and deleting a note: update(), re-add idempotency, 409, delete, raw read-back, versioning

### Takeaway
Edit = `update(data_id, data, dataset_id)`, which keeps the same data_id and by default re-ingests only changed chunks (chunk-level diff); falls back to dropping that document's graph/vector memory and rebuilding. Re-adding a changed file path gives 409; changed raw text becomes a NEW unlinked document. No version history of content exists.

### Cited Findings
- `update(data_id, data, dataset_id, user, node_set, ..., incremental_loading=True, data_cache=True, chunk_level_diff=True, graph_model=KnowledgeGraph, custom_prompt, chunker=TextChunker, policy, extractor)`: replaces exactly one document, never creates; keeps `data_id`; NOT a plain delete-then-add; default is chunk-level diff leaving untouched chunks and entities. Old relationships absent from new content are removed. Row is never deleted; failed rebuild leaves old content with no graph until next `cognify()` — [update()](https://docs.cognee.ai/python-api/update.md)
- Full rebuild fallback: `forget(memory_only=True)` for that doc (nodes shared with other docs kept), re-add pinned to same data_id, re-cognify using stored chunk size. Triggers: custom_prompt, non-default graph_model, node_set non-None, per-call db config, `chunk_level_diff=False`, unsupported chunker/backend/metadata, no baseline, chunks not tiling, unreadable text (nine reasons) — [update()](https://docs.cognee.ai/python-api/update.md)
- Returns dict `UpdateResult` always: status `incremental|unchanged|full_rebuild|failed`, chunk counts, `pipeline_run_id`, `fallback`, `error`. Failed rebuild is RETURNED not raised; over HTTP gives 500 with that body — [update()](https://docs.cognee.ai/python-api/update.md)
- Update errors: `UpdateTargetNotFoundError` 404, `PermissionDeniedError` 403, multi-item `data` lists rejected, `IngestionError` for path strings when `ACCEPT_LOCAL_FILE_PATH=false`. Pass the same `extractor` used at ingest since it is not recorded — [update()](https://docs.cognee.ai/python-api/update.md)
- Docs inconsistency: update() docstring mentions `dataset_name` but signature accepts only `dataset_id`; REST docs omit 409 for update — [update()](https://docs.cognee.ai/python-api/update.md); [PATCH /update](https://docs.cognee.ai/api-reference/update/update.md)
- REST: `PATCH /api/v1/update?data_id=&dataset_id=&chunk_level_diff=true` multipart `data` (files), optional `node_set`. Via serve()/remote, `custom_prompt`, `graph_model`, `chunker` etc. are dropped with a warning, `node_set=[]` keeps stored node set — [PATCH /update](https://docs.cognee.ai/api-reference/update/update.md); [update()](https://docs.cognee.ai/python-api/update.md)
- Idempotency of add: identical content is a no-op (returns existing data_id); raw text identified by content hash, so edited text = new document; changed file with same path/upload filename raises `DocumentUpdateRequiredError` (HTTP 409), whole request refused, nothing written — [add()](https://docs.cognee.ai/python-api/add.md); [POST /add](https://docs.cognee.ai/api-reference/add/add-low-level:-ingest-files-text-or-urls-into-a-dataset-without-building-the-graph.md)
- `datasets.delete_data(dataset_id, data_id, user, mode="soft"(ignored), delete_dataset_if_empty=False)`: removes graph nodes/edges derived from the item, vector points (incl. edge/triplet entries), relational ownership + Data row, raw file only if no other row points to it and it is under `DATA_ROOT_DIRECTORY`, best-effort session-cache entries. Leaves shared nodes (referenced by other docs), dataset record, search history. Receipt has status `success|not_found` — [datasets](https://docs.cognee.ai/python-api/datasets.md)
- 1.6.8: stored files no document references are removed after forget/update/failed updates; recovered runs no longer overwrite newer status — [changelog](https://docs.cognee.ai/changelog.md)
- Raw read-back: `list_data` returns `raw_data_location` (Python docs don't say how to read it); REST `GET /api/v1/datasets/{dataset_id}/data/{data_id}/raw` returns the original file as download (404 if missing, 501 unsupported storage scheme) — [datasets](https://docs.cognee.ai/python-api/datasets.md); [raw endpoint](https://docs.cognee.ai/api-reference/datasets/get-raw-data.md)
- `find_data(dataset_id, content=|content_hash=)` can locate a Data row by content or hash — [datasets](https://docs.cognee.ai/python-api/datasets.md)
- Versioning: node `version` counter only changes when you call `update_version()`; rewriting a node overwrites; `update()` does not keep previous content; no point-in-time query; opt-in provenance ledger (`PROVENANCE_TRACKING=true`) stores hashes/metadata only, not content; `forget()` permanent with tombstone; export a COGX snapshot before changes — [Memory versioning](https://docs.cognee.ai/core-concepts/further-concepts/memory-versioning.md)
- Conflict review keeps superseded facts visible in graph and recall results (sorted after current) — [Memory versioning](https://docs.cognee.ai/core-concepts/further-concepts/memory-versioning.md)

### Inferences
- Note identity strategy: keep own mapping note_id -> cognee data_id (from `add()`/`remember()` result `data_ids`); on edit call `update()`, on delete `datasets.delete_data()`. Do not edit by re-adding text (leaves stale document with old facts).
- Storing notes as files (stable per-note path/filename) makes accidental re-add hit 409 rather than silently duplicating — a useful guard, but handle it by calling update.
- Because update with custom_prompt/graph_model/node_set forces full rebuild, tag changes cost a full re-extraction of that note.
- Shared entities survive deletion of one note, so entity-level "ghost" nodes may persist if only that note mentioned... actually shared nodes are those used by other docs; entities exclusive to the deleted doc are removed (per "nodes derived from the item"). Confirm empirically.

### Gaps
- Exact hashing algorithm and `data_id` generation not documented.
- Behavior of graph-node deletion for entities deduplicated across documents (ownership counting) is only described in prose; not verified in source.
- Whether `update()` accepts markdown text content vs file for a note stored as raw text (docs say text, file path, file:// or s3://, ok).
- Did not verify behavior in source code (docs-only).

## 4. Concurrency, locks, single-process embedding vs separate server, REST /api/v1, auth, permissions, multi-tenancy

### Takeaway
Runs on the same dataset are serialized by an in-memory per-dataset lock; different datasets run in parallel; locks do not protect across processes. Ladybug (default graph) is single-writer and "not suitable for concurrent use from different agents or processes"; so embed one cognee in one process (or run one cognee server) and have the app talk to it, rather than two processes opening the same files.

### Cited Findings
- Per-dataset lock: same dataset serialized, different datasets parallel; deletes and `improve()` use the same lock; second improve queues (since 1.6.6). Lock is in-memory and process-local, no protection across multiple processes/API workers — [Pipelines](https://docs.cognee.ai/core-concepts/building-blocks/pipelines.md); [improve()](https://docs.cognee.ai/python-api/improve.md)
- `run_in_background=True` on add/cognify/remember/improve returns immediately; monitor via `pipeline_run_id`, WebSocket `/cognify/subscribe/{pipeline_run_id}` (one subscriber per run; second steals events; remember background runs don't publish to it), or `GET /api/v1/datasets/status/progress` — [cognify()](https://docs.cognee.ai/python-api/cognify.md); [remember()](https://docs.cognee.ai/python-api/remember.md)
- Server shutdown drains background tasks (`BACKGROUND_DRAIN_TIMEOUT_SECONDS`, default 8) and lifespan enters `pipeline_recovery_service()`; 1.6.8 checks abandoned runs every 5 minutes — [client.py](https://raw.githubusercontent.com/topoteretes/cognee/main/cognee/api/client.py); [changelog](https://docs.cognee.ai/changelog.md)
- Ladybug: local file graph at `<SYSTEM_ROOT_DIRECTORY>/databases/cognee_graph_ladybug`; runs in a worker subprocess; retries lock contention (`SUBPROCESS_OPEN_LOCK_RETRIES` 10, backoff 0.1s); idle worker holds the file lock up to `SUBPROCESS_IDLE_TTL_SECONDS` (600; 0 releases at each dataset-context exit); one writer on one machine; caps `KUZU_BUFFER_POOL_SIZE` 32 GiB, `KUZU_MAX_DB_SIZE` 128 GiB; `SYSTEM_ROOT_DIRECTORY` defaults inside the installed package, so pin an absolute path — [Graph stores](https://docs.cognee.ai/setup-configuration/graph-stores.md)
- Deployment page also says default Ladybug "uses file-based locking, so not suitable for concurrent access from multiple agents" and recommends Neo4j or FalkorDB for multi-agent — [Deployment](https://docs.cognee.ai/how-to-guides/cognee-sdk/deployment.md). That page's "local dev" stack lists NetworkX graph, which conflicts with the Ladybug default stated elsewhere (treat as stale docs).
- LanceDB: default vector store; "takes no exclusive file lock"; subprocess mode on by default (`VECTOR_DB_SUBPROCESS_ENABLED`), `SUBPROCESS_WORKER_MAX_INFLIGHT` 16, concurrent add/search run in parallel; compaction holds write lock; macOS fd limit caveat. `EMBEDDING_DIMENSIONS` must match; one embedding model per dataset; changing model requires re-embed (EmbeddingDimensionMismatchError 409 in multi-user mode) — [Vector stores](https://docs.cognee.ai/setup-configuration/vector-stores.md)
- SQLite relational default for local dev, Postgres for production — [Permissions setup](https://docs.cognee.ai/setup-configuration/permissions.md); [Docker](https://docs.cognee.ai/how-to-guides/cognee-sdk/deployment/docker.md). Concurrency specifics of SQLite not documented on pages read.
- REST server: `uvicorn cognee.api.client:app --host 0.0.0.0 --port 8000`, or `python cognee/api/client.py` (`--agent-mode` -> port 8011); `HTTP_API_HOST`/`HTTP_API_PORT`; Swagger at `/docs` — [Deploy REST API](https://docs.cognee.ai/guides/deploy-rest-api-server.md)
- `client.py` defines module-level `app` and includes routers via `get_*_router()` factories under: `/api/v1/` auth, add, cognify, memify, search, permissions, conflicts, datasets, ontologies, settings, visualize, schema, provenance, skills, proposals, configuration, delete, validate, update, responses, llm, sync, users, checks, agents, activity, sessions, remember, recall, improve, forget, slack, integrations; plus `/health` and `GET /`. No helper for mounting; no `root_path`; CORS from `CORS_ALLOWED_ORIGINS` (fallback `UI_APP_URL`); methods OPTIONS/GET/PUT/POST/DELETE (NOT PATCH, though `PATCH /api/v1/update` exists — cross-origin browser calls to update may be blocked by CORS; the Phibe frontend should go through its own backend) — [client.py](https://raw.githubusercontent.com/topoteretes/cognee/main/cognee/api/client.py)
- Auth: `ENABLE_BACKEND_ACCESS_CONTROL` "true by default" when storage supports it (auto-enabled if Ladybug/LanceDB etc.); with it on, auth is required and default user has no password unless `DEFAULT_USER_PASSWORD` set -> every `/api/v1` call is 401. `REQUIRE_AUTHENTICATION` inherits and is ignored as false while access control is on. Single-user mode: `ENABLE_BACKEND_ACCESS_CONTROL=false` disables auth and permissions — [Permissions setup](https://docs.cognee.ai/setup-configuration/permissions.md); [Docker](https://docs.cognee.ai/how-to-guides/cognee-sdk/deployment/docker.md)
- Login: `POST /api/v1/auth/login` form fields `username`,`password` -> `access_token`; use `Authorization: Bearer` or cookie; API keys via `X-Api-Key`. `JWT_LIFETIME_SECONDS` default 3600; `FASTAPI_USERS_JWT_SECRET` has no default (random per process -> tokens break on restart/multi-process, so pin it); `HASH_API_KEY` default False (plaintext keys); `AUTH_TOKEN_COOKIE_SECURE` default false — [Security](https://docs.cognee.ai/setup-configuration/security.md); [Deploy REST API](https://docs.cognee.ai/guides/deploy-rest-api-server.md)
- Default user email `default_user@example.com`; used by SDK calls when `user=None` — [Permissions setup](https://docs.cognee.ai/setup-configuration/permissions.md); [add()](https://docs.cognee.ai/python-api/add.md)
- Dataset permissions read/write/share/delete; names resolve only for owned datasets, shared need UUID; `improve` needs write; datasets named in `search` that cannot be resolved raise 404. Permission endpoints exist for roles, tenants, principals, capabilities — [Data isolation](https://docs.cognee.ai/core-concepts/multi-user-mode/data-isolation-and-multi-tenancy.md); [llms-api index](https://docs.cognee.ai/llms-api.md); [search()](https://docs.cognee.ai/python-api/search.md)
- Security defaults that affect a local app: API server refuses server-side file paths unless `ACCEPT_LOCAL_FILE_PATH` set (1.6.7), refuses URLs unless `ALLOW_HTTP_REQUESTS` (1.6.8), DB connection strings unless `ALLOW_DATABASE_INGESTION` — SDK/CLI calls remain allowed — [Security](https://docs.cognee.ai/setup-configuration/security.md); [changelog](https://docs.cognee.ai/changelog.md)
- Remote mode: Python `serve()` redirects remember/recall/update to REST and silently drops several local-only parameters (auto_route, user, llm_config, update's custom_prompt/graph_model/chunker...) — [recall()](https://docs.cognee.ai/python-api/recall.md); [update()](https://docs.cognee.ai/python-api/update.md)
- Rate/budget: `LLM_RATE_LIMIT_*` and `AUTO_RATE_LIMIT` env; improve honors HTTP 402 budget exhaustion — [cognify()](https://docs.cognee.ai/python-api/cognify.md); [improve()](https://docs.cognee.ai/python-api/improve.md)

### Inferences
- Several cognify runs on different datasets can run concurrently; on the SAME dataset they queue. Since Ladybug is single-writer with subprocess, concurrent writes to one graph file still pass through one worker; for a single-user app, pick one dataset per workspace/area and avoid parallel edits storms (queue note edits in the app).
- Embedding cognee inside Phibe's FastAPI process: supported implicitly by calling the Python API directly (all operations are async), single process holds the Ladybug lock. Mounting cognee's `app` or routers is possible via the `get_*_router()` factories but undocumented as a supported pattern (and the lifespan—migrations, default user, recovery—would not run unless you call it). Running a separate cognee server avoids event-loop and dependency-conflict issues but then you must manage auth tokens, CORS (PATCH missing) and the single-process-writer rule yourself.
- For a local single-user second brain, `ENABLE_BACKEND_ACCESS_CONTROL=false` is simplest but disables dataset filtering (all datasets in one graph/vector instance, filters ignored). If you rely on separate datasets for isolation, keep access control ON and set `DEFAULT_USER_PASSWORD` (SDK default user needs no token). This trade-off is important and should be decided early.

### Gaps
- Not confirmed how multiple concurrent `cognify()` calls on the same dataset behave beyond "serialized"; whether the second returns AlreadyCompleted after the first is plausible but not documented.
- SQLite locking/concurrency specifics (WAL, busy timeout) not found.
- Whether mounting routers in an existing FastAPI app works without cognee's lifespan: not documented; I did not read the source of the router factories.
- 409 semantics: add (file changed), cognify (ontology key missing), progress (status retrieval failed), EmbeddingDimensionMismatch, session-dataset conflict — all different causes; no single 409 meaning.

## 5. Observability, graph view/export, backup/restore/reset

### Takeaway
Observability is decent (pipeline_runs table, progress endpoint, activity/spans, per-model cost endpoint, dry-run cost estimates), graph viewing is via `visualize_graph` HTML or REST visualize endpoints, but there is no documented backup/restore procedure and prune is global and destructive.

### Cited Findings
- Pipeline status: `datasets.get_status(dataset_ids, pipeline_names)`, `GET /api/v1/datasets/status/progress` (`dataset`, `pipeline` params; returns `{status, progress{completed_items,total_items,current_stage}}`; statuses INITIATED(legacy)/STARTED/COMPLETED/ERRORED) — [datasets](https://docs.cognee.ai/python-api/datasets.md); [progress endpoint](https://docs.cognee.ai/api-reference/datasets/get-dataset-progress.md)
- `get_memory_status(dataset_ids)`: combined state (`empty`, `indexing`, `ready`) from relational tables only — [datasets](https://docs.cognee.ai/python-api/datasets.md)
- `pipeline_runs` rows share one `pipeline_run_id`; only the terminal row carries outcome and token counts; `parent_operation_id` forms a tree and parents already include child spend (sum one level only) — [Pipelines](https://docs.cognee.ai/core-concepts/building-blocks/pipelines.md)
- 1.6.6: `pipeline_runs.run_info` no longer stores run input — [changelog](https://docs.cognee.ai/changelog.md)
- Always-on operations log at `GET /api/v1/activity/pipeline-runs`; also activity spans (needs `COGNEE_TRACING_ENABLED` for trace data) — [Memory versioning](https://docs.cognee.ai/core-concepts/further-concepts/memory-versioning.md); [Deploy REST API](https://docs.cognee.ai/guides/deploy-rest-api-server.md)
- Cost/tokens: `GET /api/v1/sessions/cost-by-model?range=24h|7d|30d|all` (schema unspecified; session-based), `dry_run=True` on cognify/remember gives token+USD estimates — [cost-by-model](https://docs.cognee.ai/api-reference/sessions/cost-by-model.md); [cognify()](https://docs.cognee.ai/python-api/cognify.md)
- Logging: `LOG_LEVEL` (default INFO), `COGNEE_LOGS_DIR` (default `~/.cognee/logs`, absolute only), file per startup, keep 10, rotation 50 MB x 5; set LOG_LEVEL before `import cognee` — [Logging](https://docs.cognee.ai/setup-configuration/logging.md)
- Telemetry: `TELEMETRY_DISABLED` any non-empty value (even "false") disables; off when `ENV` is dev/test; sends op names/IDs not content to `https://test.prometh.ai` — [Security](https://docs.cognee.ai/setup-configuration/security.md)
- Graph viewing: `visualize_graph(path=None, *, dataset, full=False, query, seed_node_ids, recall_result, neighborhood_depth=2, neighborhood_seed_top_k=10, max_nodes=500)` writes HTML (home dir by default) and returns the string; REST `GET /api/v1/visualize` (HTML) and `/visualize/json` (payload; SSE streaming raises max_nodes 5000 -> 20000); HTML has Graph/Schema/Memory/Semantic tabs — [Graph visualization](https://docs.cognee.ai/guides/graph-visualization.md)
- Other read/export surfaces: `GET /api/v1/datasets/{id}/graph`, `datasets.sparql()` read-only SPARQL, `GET /api/v1/datasets/graph summary`, `export-dataset-markdown` in activity, COGX snapshot format, provenance JSONL export — [llms-api index](https://docs.cognee.ai/llms-api.md); [datasets](https://docs.cognee.ai/python-api/datasets.md); [Memory versioning](https://docs.cognee.ai/core-concepts/further-concepts/memory-versioning.md)
- `prune.prune_data()` deletes all raw data files (not DB records); `prune.prune_system(graph=True, vector=True, metadata=False, cache=True)` deletes graph, vector, optionally relational metadata (datasets, data records, pipeline state), cache dir and session cache. Both global, no dataset_id, no permission checks; docs limit it to dev/test. It does NOT reset per-item cognify status, so cognify may skip items; to rebuild one dataset use `forget(dataset=..., memory_only=True)` then `cognify`. Per-dataset: `datasets.empty_dataset(dataset_id)`, per-item `datasets.delete_data` — [prune](https://docs.cognee.ai/python-api/prune.md)
- `empty_dataset` deletes graph content, data records AND the dataset entity; purges all users' search history for it — [datasets](https://docs.cognee.ai/python-api/datasets.md)
- Persisted state locations: raw files `DATA_ROOT_DIRECTORY`, system DBs (SQLite, Ladybug, LanceDB) under `SYSTEM_ROOT_DIRECTORY/databases` (default inside the package unless pinned), cache `CACHE_ROOT_DIRECTORY`. File-based migration: stop Cognee, copy `databases/` folder — [Graph stores](https://docs.cognee.ai/setup-configuration/graph-stores.md); [prune](https://docs.cognee.ai/python-api/prune.md); [Deployment](https://docs.cognee.ai/how-to-guides/cognee-sdk/deployment.md)
- Docs explicitly state no documented backup procedure for the Ladybug file / Docker volumes; `docker compose down --volumes` deletes all data — [Graph stores](https://docs.cognee.ai/setup-configuration/graph-stores.md); [Docker](https://docs.cognee.ai/how-to-guides/cognee-sdk/deployment/docker.md)
- Web UI: Docker profile `ui` at port 3000 (`COGNEE_BACKEND_URL`, CORS must include UI origin); do not run `cognee.start_ui()` simultaneously (same port) — [Docker](https://docs.cognee.ai/how-to-guides/cognee-sdk/deployment/docker.md)

### Inferences
- Safest "backup" for a local file-based setup: stop the process (Ladybug lock, idle TTL 600s unless `SUBPROCESS_IDLE_TTL_SECONDS=0`), then copy `SYSTEM_ROOT_DIRECTORY` and `DATA_ROOT_DIRECTORY` together (relational IDs reference raw files and vector/graph IDs). Raw notes should remain the source of truth in Phibe's own storage so the graph can be rebuilt (`forget memory_only` + `cognify`, or prune + re-add).
- Never call `prune_system` in production code paths of Phibe; use dataset-scoped forget/empty.
- Per-call cost visibility for Phibe likely needs the `cost-by-model` endpoint or `dry_run`; per-cognify token counts are in the terminal `pipeline_runs` row (DB read).

### Gaps
- `cognee.start_ui()` and GraphML/other graph export formats: not documented on pages read (graph visualization page says so). Not confirmed.
- Response schema of `cost-by-model` not specified.
- No documented restore procedure; the COGX export/import (`migrate-memory-systems` page) was not read.
- Whether `visualize_graph` honors dataset in single-user mode is not documented.

## 6. Deployment page: Docker, local, performance notes

### Takeaway
Docs provide Docker/Compose/Helm/EC2/Coolify options; local file-based stack (SQLite + LanceDB + Ladybug) is "single-process, small single-tenant". The deployment overview has no performance numbers or resource sizing.

### Cited Findings
- Docker one-liner: `docker run -p 8000:8000 -e LLM_API_KEY=... -e ENABLE_BACKEND_ACCESS_CONTROL=false -v cognee_storage:/cognee-storage cognee/cognee:main`; volumes needed (`/cognee-storage`), container runs as uid 1000; `docker compose --profile postgres|neo4j|mcp|ui` ; healthcheck `GET /health` every 30s (does not test ingestion/graph/recall); `ENABLE_AUTO_MIGRATIONS` default true (`cognee-cli upgrade` for manual) — [Docker](https://docs.cognee.ai/how-to-guides/cognee-sdk/deployment/docker.md)
- Docker env defaults: `DB_PROVIDER=sqlite`, `VECTOR_DB_PROVIDER=lancedb`, application default graph `ladybug` (`.env.template` sets kuzu), `LLM_MODEL=openai/gpt-5.6-luna`, `CORS_ALLOWED_ORIGINS=*` in Compose, `COGNEE_SKIP_CONNECTION_TEST=false` — [Docker](https://docs.cognee.ai/how-to-guides/cognee-sdk/deployment/docker.md)
- Without `LLM_API_KEY` cognee runs keyless (GLiNER + fastembed) — [Docker](https://docs.cognee.ai/how-to-guides/cognee-sdk/deployment/docker.md); [cognify()](https://docs.cognee.ai/python-api/cognify.md)
- Production options: Coolify, Kubernetes Helm, EC2, managed DBs (RDS, Neo4j Aura, Qdrant). Default Ladybug not for concurrent multi-agent access; use Neo4j/FalkorDB; Neo4j Community supports one DB per server so multi-user handler runs one container per dataset (cap 6); `postgres_demo` graph is demo only — [Deployment](https://docs.cognee.ai/how-to-guides/cognee-sdk/deployment.md); [Graph stores](https://docs.cognee.ai/setup-configuration/graph-stores.md)
- Local/Python install with `uv sync --all-extras` and uvicorn; no mention of Windows specifics — [Deploy REST API](https://docs.cognee.ai/guides/deploy-rest-api-server.md)
- Latest changes relevant to ops (1.6.4-1.6.8): LanceDB worker processes cleanup, Ladybug writes checkpoint immediately, locks work across event loops/threads, filesystem session cache removed (use SQL/Redis `CACHE_BACKEND`) — [changelog](https://docs.cognee.ai/changelog.md)
- Cost control: `dry_run`, `summary_method=from_extraction`, `GRAPH_EXTRACTOR` (GLiNER keyless), `LLM_RATE_LIMIT_*` — [cognify()](https://docs.cognee.ai/python-api/cognify.md)

### Inferences
- Docker is not required for Phibe; installing cognee as a Python dependency and calling the API in-process (one process, pinned `SYSTEM_ROOT_DIRECTORY`/`DATA_ROOT_DIRECTORY`) matches the documented "single-process services" fit, but the docs list no Windows-specific guidance (Ladybug file locks on Windows untested here).
- Cost per note is dominated by graph extraction LLM calls (one per chunk), plus conflict review in improve (1.6.6+ default on); keep `summary_method=from_extraction`.

### Gaps
- No performance/latency/throughput numbers, resource sizing, or worker/concurrency guidance found in the deployment overview (page itself says to ask elsewhere).
- Windows support for Ladybug/LanceDB subprocess mode not covered in pages read.
- Did not read Helm/EC2/Coolify/Docker Compose Reference pages or changelog beyond the first 100k characters (page is ~695k characters).
- Docs-vs-reality conflicts spotted: NetworkX in deployment overview vs Ladybug default; `.env.template` kuzu vs application default ladybug; update() docstring `dataset_name` vs signature; search REST `include_references` default (prose true, schema false); cognify REST camelCase (OpenAPI) vs snake_case (prose) field names.
